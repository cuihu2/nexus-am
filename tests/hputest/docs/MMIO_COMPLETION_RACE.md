# MMIO 完成轮询竞态修复记录与 06 语义纠正

## 当前 06：纯 MMIO DMA 状态同步

06 的测试点是无 PSYNC 的数据回环。当前流程为：

`DLOAD → MMIO 观察 BUSY 1→0 → DSTORE → MMIO 再次观察 BUSY 1→0 → invalidate → 逐 4096 系数自检`

06 不发 PSYNC，不读写 `CSR_IRQ`，不调用 PLIC 中断路径。每次提交 DMA 前
重新清零 `saw_busy`；必须观察到本次 DMA 忙过且随后空闲，才允许继续。
分成两个阶段是因为 MMIO BUSY 来自 DMA busy：DLOAD 与 DSTORE 之间的空闲
不能作为 DSTORE 已完成的证据。命令尚未开始时的初始空闲同样不能通过。

若 CPU 未采到某次 DMA 的 BUSY=1，用例保守地超时报失败，不把缺少观测证据
解释成成功，也不据此单独认定 RTL 有错。状态故障检查、窗口有效检查、原有
超时上限、输出缓存失效和逐系数比较均保留。

07 的 DLOAD+DSTORE+PSYNC/CPU 中断流程和 09 的模表屏障、计算阶段
PSYNC+MMIO 完成轮询不在本次变更范围内。下面的 IRQ/BUSY 竞态机制说明
对当前 09 和共享 PSYNC 完成等待函数仍然有效，**不再描述当前 06**。

## 历史现象与证据范围

用户提供的 IT 失败截图对应 06 冒烟用例的完成轮询：先读取 STATUS，
再读取 IRQ；IRQ 有效即跳出，随后用旧 STATUS 的 BUSY 位判失败。
修复前的 06 存在这一时序问题，09 的最终计算阶段当时也使用相同写法。
即使硬件正常完成，两个 MMIO 读取之间的状态变化也可能触发 `case_fail()`。

本次未取得完整 VCS 日志、波形和当次 ELF，不能仅凭截图确定当时 STATUS
一定为 `0x3`，也不能认定 DMA 方向配置就是该次失败的原因。
保留截图中的 DMA 方向线索供修复后复测使用，不修改 RTL。

## 历史修复 a51d3962 的范围

`a51d3962` 修正了错误方案内部的轮询竞态，但当时仍让 06 发 PSYNC 并等 IRQ，
没有纠正其“不使用 PSYNC 的 MMIO 状态同步”测试语义。以下保留为历史记录，
不是当前 06 的实现要求：

- 06、09：每轮先读 IRQ，再读 STATUS；只有本轮观察到 IRQ 有效、窗口有效且
  BUSY 清零才退出。IRQ 先到但 BUSY 尚未清零时继续等待，不复用旧状态报错。
- `completion_wait()`：IRQ 后重新采样 STATUS，BUSY 暂未清零时继续有界等待。
- 迁移用例共用的 `wait_irq()`：同样要求完成通知与空闲状态均成立后再返回。
- 故障仍立即失败；一直忙、没有完成通知等情况仍受原有超时限制。
  未增加超时上限，也未去掉清 IRQ、缓存处理或逐系数比较。

两次 MMIO 读取并不是原子快照，本修复也不将它们视作原子快照。
等待期间不能提交下一阶段；收到并消费当前事件后，才允许继续发指令。
CPU/PLIC 中断路径、inline-asm 分支和指令编码均未在该次修复中修改。

## 验证与复测

主机回归覆盖错位读取、IRQ 先到/BUSY 延迟清零、永久 BUSY、缺少 IRQ、
故障、清除通知及数据比较失败；它只模拟 MMIO 读取顺序，不替代 RTL 仿真。
上述回归验证的是 PSYNC 完成轮询。当前 06 的回归应另外覆盖两次独立的
BUSY 1→0、启动延迟、阶段间空闲、未观察到忙状态、持续忙、故障和数据比对
失败，并拒绝任何 PSYNC、IRQ 寄存器访问或 PLIC 等待，避免再次偏离测试点。
